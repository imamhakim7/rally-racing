## 1. Change surface (trust-relevant)
Client-side TypeScript only. New: src/race/{types,stage,race,results,session,hud,index}.ts,
scripts/screenshot-race.mjs, docs/*, README, one package.json script. Modified: the engine
composition hooks (src/engine/app.ts,index.ts) and src/main.ts. No server, no API, no auth,
no persistence (all explicit non-goals in the openspec).

## 2. Trust boundaries (STRIDE)
TB1 Browser DOM  <-> race HUD.       TB2 developer-authored stage data -> state machine.
TB3 Keyboard events -> gate crossings. TB4 dev-only static file server (e2e). TB5 deps/build.
- Spoofing: n/a — no identity, no authn/authz, no network, single local player.
- Tampering: stage data and gate events are injected by trusted game code. The controller is
  client-authoritative and a player can edit their own score in devtools, but there is no
  server, no comparison across players and no persistence, so this is not a security boundary
  yet (residual risk R1). defineStage() rejects malformed/duplicate/non-dense stages.
- Repudiation: n/a — no server-side action to audit.
- Information disclosure: no PII, no secrets, no network calls. HUD renders every dynamic
  value through Node.textContent (never innerHTML), grepped clean below.
- Denial of service: update(dt) sanitises input (rejects non-finite/<=0, clamps to maxDelta),
  so NaN/Infinity or a huge stalled-tab delta cannot poison the clock; keyword handler ignores
  auto-repeat; all loops are bounded by checkpoint count.
- Elevation of privilege: n/a — no auth surface.

## 6. Residual risk (accepted, non-blocking)
R1 (Low) Race results are client-authoritative with no server validation. Acceptable while
   single-player and unpersisted; if competitive/networked results are added, totals MUST be
   validated server-side. Not in this ticket's scope.
R2 (Low) Production bundle ships sourcemaps (vite build.sourcemap=true, pre-existing APEX-1
   config). Exposes source, not secrets. Consider disabling for production in a follow-up.
R3 (Low) Playwright launches Chromium with --no-sandbox in the dev/test harness (pre-existing
   across all screenshot scripts); the served content is the locally-built dist/ only.
R4 (Info) The engine renders the HUD once per fixed step and again on onRender (redundant work);
   cosmetic, no security impact.
